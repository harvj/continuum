# P1.1 — Proposed Rails foundation and repeatable import

Status: the v0.1.0 foundation delivers Rails, PostgreSQL and host routing.
The content model and import work are proposed. Production work belongs to P1.4 and requires explicit authorization.

## 1. Establish a reproducible local foundation

Select supported Ruby, Rails and PostgreSQL versions at implementation time;
pin Ruby and resolved gems and document PostgreSQL setup. Create one Rails app
in this repository without replacing preservation scripts or source files. Use
PostgreSQL in development/test and Rails built-in facilities before new libraries.
Document setup, database creation, migrations, test and import commands. Add
an environment example with placeholders only; keep actual credentials ignored.

Route each intended host to a separate home/navigation surface inside the same
app, with local test host equivalents and an explicit allowed-host list. Use
configured host-aware URL helpers for cross-interface links. Decide unknown-host
behavior explicitly and test it. No AI chat endpoints or services.

Acceptance: a fresh local setup can migrate PostgreSQL, run application tests,
and resolve both host-specific roots without a server connection.

## 2. Define shared records and provenance

Proposed model responsibilities (names can change during implementation):

| Record | Responsibility and constraints |
| --- | --- |
| Source archive / import run | Source system, original filename, export SHA-256, parser version, run outcome and counts; preserve prior snapshots and reports |
| Source record / revision | Stable source namespace plus exported post ID; exact original URL, raw date strings, HTML/item XML, attribution evidence and source snapshot reference; retain changed revisions |
| Content item | Shared addressable article, source page, prompt, response or other item; points to source evidence; optional ordered parent/context for later conversation extraction |
| Yod | Stable identity 0–21 and reviewed name; associated source content; identity independent of placement and links |
| Tableau placement | Tableau/version, Yod reference, row and column; unique position and Yod per tableau; layout can change without changing identity |
| Concept / explicit relationship | Addressable typed concepts and typed links with source/review provenance; integer, Hebrew-word or correspondence data only when evidenced |
| Media asset / usage | Original file identity, filename, MIME, size, SHA-256, exported URL variants, requested/final URLs, attribution if available, page usage and Active Storage attachment |

Avoid separate copies of the same article for Library and Intelligence. An initial
source page need not be guessed to be an article or split into roles. Keep unparsed
metadata available; store parsed dates separately from exported strings, and record
parse failures without inventing dates or authors. Original exports remain external,
immutable evidence; item serialization is not a byte-exact replacement.

Start with the minimal model required for Squarespace and verified Yods; defer
unused concept-specific fields and conversation parsing to later milestones.
Use database foreign keys, uniqueness and validation for stable identities and
explicit relationships. Never treat the numeral in a hexagram title as a Yod key.

Acceptance: model tests preserve Unicode and nullable metadata, prohibit duplicate
source keys and placements, and show layout changes do not alter Yod identity.

## 3. Build an auditable, repeatable Squarespace importer

1. Regenerate fresh inventory rather than consuming the stale local JSON. Define
   and test a versioned interchange contract between Python extraction and Rails;
   reject missing required contract fields rather than silently dropping evidence.
2. Provide proposed command `bin/rails import:squarespace` with explicit input
   locations and dry-run behavior. Dry run validates source checksums, records,
   media and identities, reports intended changes, and writes no application data.
3. Scope stable keys by source system/site and exported post ID. Missing IDs and
   conflicting duplicates require review; do not fall back silently to array index
   or title. An export checksum identifies a snapshot, not a new content identity.
4. Upsert shared records under database constraints, preserve revisions, and
   record created/updated/unchanged/rejected counts. Unchanged runs create no new
   content, revisions or attachments; separate run audit records are permitted.
5. Preflight missing/invalid media and ambiguous identities. Use transactions for
   database changes and staged attachments with explicit recovery: disk writes are
   not rolled back by SQL. Keep a recoverable run ledger; never purge originals.
6. Treat absent records in later snapshots as a reconciliation report, not deletion.
   Keep old media usage/provenance and archived manifests; URL aliases or changes
   need evidence before merging records. Prevent concurrent duplicate imports.
7. Retain original links and HTML. Build resolved internal-link mappings separately;
   sanitize only rendered HTML with an explicit allowlist. Strip active content and
   unsafe URL schemes from views without rewriting preserved source evidence.

Acceptance: a first real-source run accounts for all 37 pages without problems;
second unchanged run creates zero duplicate content/media. Synthetic fixtures test
changed snapshots, duplicates/conflicts, missing fields/files, malformed input,
partial failures and resumed runs. Checksums prove source files unchanged.

## 4. Integrate preserved local media

Use Active Storage disk service locally and on Hetzner. Production root will be an
absolute persistent path selected during deployment preparation, outside releases.
No S3/CDN. Verify all 55 existing files before attachment and stream original bytes
without transcoding. Keep original filenames, URL variants, source-page usage and
available attribution separately from generated storage keys. Reuse one verified
asset across content entities; do not infer identical provenance from identical bytes.

Support attachments to articles, Yods, hexagrams and future content entities using
built-in attachment associations. Keep optional variants/derivatives separate from
originals and record processing provenance. Do not delete legacy `media/` originals
or preservation manifests after attaching. Decide how media is served under both
hosts and test generated URLs to avoid broken cross-host attachments.

Acceptance: tests with small local fixtures verify attachment byte hashes, filename
and provenance preservation, shared usages, rerun reuse, and recovery from a failed
attachment. No network download is needed for these tests. Persistent storage and
off-server restoration requirements remain explicit deployment gates.
